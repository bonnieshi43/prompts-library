## ⚠️ 必须正视的主要困难

在汇报计划之前，需说明以下客观困难，避免后续产生预期偏差：

**1. 现有测试质量低，不能只看数量**  
338 个现有 spec 大量使用 CSS 选择器和快照测试，覆盖的多是最简单的服务路径，**组件模板行为和用户交互几乎未覆盖**。"迁移+提质"双重工作量，比单纯新增 spec 复杂。

**2. 框架必须先升级，再扩展**  
当前框架（Jest）与目标框架（Vitest）并存会造成双倍维护成本。**框架迁移是前置动作**，不迁移就批量写新测试等于埋雷，因此第一周必须先做迁移，后续效率才能释放。

**3. E2E 测试需要人工深度介入，速度慢于预期**  
E2E 不是纯写代码，涉及：case 设计、Docker 环境准备、真实实例联调、前端 debug 定位。**每条 E2E case 的调试成本远高于 Unit 测试**，必须由懂 Angular 的前端工程师 + QA 工程师协作完成，速度以模块优先级推进，不能并行铺开。

**4. Composer 重设计带来写了白费的风险**  
Composer 的外壳容器（布局/工具栏）即将被整体替换，现在写这部分测试会作废。已明确区分"现在写"（内部逻辑组件）和"等稳定后写"（外壳容器）两类，**这是主动规避浪费，不是拖延**。

**5. 补充测试 case 的过程中，会暴露大量存量 bug**  
这是测试覆盖率提升的必然副产品，也是本次工作的核心价值之一。当前 74% 的代码从未被系统测试覆盖，意味着其中潜伏的问题从未被自动化手段验证过。在批量补充 case 的过程中，预计会持续发现以下几类问题：

- **逻辑边界 bug**：组件在特定输入/状态组合下的异常行为，日常手测难以覆盖
- **服务调用异常**：HTTP 错误处理、空值传递、订阅未释放等
- **UI 交互缺陷**：条件渲染错误、表单校验遗漏、事件未正确传递

**这些 bug 必须在发现后快速修复，否则新增的 spec 无法通过，测试推进会被阻塞。** 修复工作需要前端工程师介入，会与写 case 的工作量交织在一起，是计划中必须预留的缓冲时间来源。保守估计，**每周新增 case 所触发的 bug 修复，会占用前端工程师约 20–30% 的工作时间**。这部分已在各阶段工作量中隐含考虑，但若 bug 密度超出预期，需及时同步并调整排期。

## 🧭 整体推进策略

三类测试工作的推进方式不同，需要明确分工而非混在一起排期：

| 类型 | 推进方式 | 原因 |
|------|----------|------|
| **Component Unit Case（主线）** | FE + QA 主力全力推进 | AI 辅助自动化率 80–95%，无环境依赖，效率最高，是短期内拉升覆盖率的核心手段 |
| **E2E（并行支线）** | QA 独立推进，不占主线节奏 | 有现成基础设施，QA 可独立操作，但每条 case 调试成本高，不能作为主线 |
| **Stagehand AI 冒烟（并行支线）** | QA 独立推进，硬 deadline 约束 | 必须在 composer2026 Stage 2 启动前就绪，时间窗口明确，但搭建工作相对独立 |

> **核心原则：Unit case 是主线，效率最高、收益最快；E2E 和 Stagehand 并行推进但不挤占主线资源，不以它们的进度衡量整体测试进展。**

## 🗓 短期计划（第 1–2 周）

> **目标：框架升级解锁主线，Unit case 快速起量；E2E/Stagehand 同步启动不阻塞**

### Week 1｜框架迁移 + 主线试点 + 支线启动

**主线：FE 工程师**

| 任务 | 内容 | 工作量 |
|------|------|--------|
| **Vitest 框架迁移** | 338 个 Jest spec 机械迁移到 Vitest（`jest.fn` → `vi.fn`），28 个快照文件一键再生成，全量跑通 | **2天** |
| **Portal 共享 Tier 1 试点（10个）** | 迁移完成后立即启动，验证"源码阅读 + Playwright MCP 组合"生成工作流，为后续批量生产定标准 | **2天** |
| **存量 bug 快速修复** | 试点过程中发现的 spec 失败，定位并修复对应组件 bug | **0.5天（预留缓冲）** |

**并行支线：QA 工程师**

| 任务 | 内容 | 工作量 |
|------|------|--------|
| **Stagehand 环境搭建** | 配置 Stagehand 连接 StyleBI 实例，跑通第一条 Composer 冒烟工作流 | **2天** |
| **E2E 7个 portal spec 启动** | 将已有 Markdown 计划转为 TypeScript（仓库树/收藏夹/搜索等），使用 AI 流水线辅助生成，先跑通 2–3 条 | **3天** |

**Week 1 验收标准：**
- ✅ 338 个 spec 在 Vitest 下全部通过
- ✅ 试点 10 个 Tier 1 组件 spec 通过 review，批量生产流程验证完毕
