# PR #3515 测试分析报告（Feature #74657）
## ⚠️ 前提条件(测试前必读)

**系统属性 `graph.svg.inline` 必须设置为 `true`,本报告涉及的全部内容才具备可测性。**

## 第一部分：Requirement Summary（需求概要）

- **核心目标**：将所有图表类型（柱状、折线、面积、散点、蜡烛、箱线、雷达、树图、旭日图、层级图、马赛克图）的入场动画时长、缓动函数与元素间隔（stagger）节奏统一，对齐 swaker look-and-feel 设计参考，消除各图表类型间动画风格不一致的问题。
- **用户价值**：提升仪表盘中多图表动画的视觉一致性和专业观感；解决动画播放期间 hover 高亮/变暗效果与动画本身冲突导致的视觉闪烁问题；此外折线图、面积图借此新增了此前完全没有的 hover 高亮/变暗交互能力。
- **Feature 类型**：UI / Rendering（图表入场动画与 hover 交互）。

---

## 第二部分：Implementation Change（变更分析）

### 核心变更

1. **新增统一动画常量 `AnimationConstants`**：`DURATION=0.8s`、`EASING=ease-out`、`STAGGER_WINDOW=2.0s`，取代原先各图表类型硬编码、互不一致的时长（0.6s/0.8s/0.9s/1.2s）、缓动函数与间隔算法。
2. **Stagger（错落间隔）算法根本性改变**：旧算法为"每元素固定步长，总耗时随元素数量线性增长（部分带上限）"；新算法 `staggerDelay(index, count) = index * STAGGER_WINDOW/(count-1)` 使**总错落窗口固定为 2 秒**，不论元素多少，首尾延迟差恒定。
3. **柱状图默认动画方式改变**：`BAR_GROW_ENABLED` 默认为 `false`，柱子默认改为**纯透明度淡入**，不再默认使用原先"从基线 Y 轴缩放生长"的动画（该效果仍保留为可切换的编译期开关，但默认行为已变）。
4. **新增 `.ready` 门控机制（跨前后端协作）**：Java 端计算并在 SVG 根元素输出 `data-last-delay` 属性；Angular 指令 `ChartInlineSvgDirective` 在 SVG 加载后延迟 `DURATION+READY_BUFFER≈0.9s` 才为 SVG 添加 `.ready` class。点图、蜡烛图、箱线图、树图、马赛克图、雷达图（"A1 类"，动画直接作用于 hover 目标分组本身）的 hover 变暗 CSS 规则改为依赖 `svg.ready:has(...)` 选择器；面积图/折线图新增的 hover 高亮功能同样通过 `svg.ready` 门控；仅柱状图（动画作用于内部子元素，不与 hover 目标冲突）未加此门控，hover 变暗立即生效。
5. **折线图/面积图动画时长缩短**：擦除（wipe）/绘制（draw）动画从硬编码 1.2s 改为 `AnimationConstants.DURATION`(0.8s)；ghost fill（半透明底色）从"独立淡入"改为"与主线擦除同步的 clip-path 从左至右擦除"。
6. **面积图新增鼠标交互高亮功能（非纯动画范畴的新功能）**：新增 `setupAreaHover`/`onAreaMouseMove`/`getScreenYAtX`（对 SVG Path 做二分查找定位屏幕 Y 坐标），鼠标移动时高亮距离最近的面积/线系列，其余系列变暗 0.2 透明度；面积填充算法从"各系列独立半透明多边形"改为"相邻系列间重塑为不重叠色带（band polygon）"。
7. **各分层图表（treemap/sunburst/icicle/mekko）内部排序算法重写**：环形优先级、深度优先级、对角线比例缩放等排序逻辑基本保留，但延迟数值全部重新映射进固定的 `STAGGER_WINDOW`，测试文件中的预期数值已相应更新（如 icicle 层级延迟由 0.25/0.50 改为 1.00/2.00）。

### 目标覆盖度

PR 对"标准化各图表类型动画模式与间隔"这一 Feature 描述已做系统性覆盖，所有图表类型均已迁移到统一常量体系。但 PR 中还引入了 Feature 描述未提及的两项独立新功能——**面积图鼠标就近高亮交互**与**面积色带（band）重新渲染**——这两项是否属于"动画对齐设计参考"范围内，因缺少设计稿细节无法判定，需与产品/设计确认是否为预期范围，且需按功能而非纯动画视角单独验证。

### 行为变化对比表

| Before Behavior | After Behavior | Risk |
|---|---|---|
| 各图表类型动画时长/缓动不一致（0.6s/0.8s/0.9s/1.2s，ease-out/ease/cubic-bezier 混用） | 统一为 `DURATION=0.8s` + `EASING=ease-out` | Rendering — 折线/面积等动画整体变快（1.2s→0.8s），视觉节奏改变，需与设计稿比对 |
| stagger 总时长随元素数量增长（部分有 cap，如 `min(colIdx*0.12, 2.0)`） | stagger 总窗口固定 2.0s，元素越多间隔越密 | Functional — 少量数据点（如 2 个系列）的错落间隔从原先很短变为达到完整 2s，动画观感显著变慢 |
| 柱状图默认从基线缩放"生长"进入 | 柱状图默认纯透明度淡入 | Functional/Compatibility — 默认视觉效果改变，依赖旧效果的回归截图/演示材料需同步更新 |
| hover 变暗 CSS 无门控，SVG 加载后立即可触发 | A1 类图表 hover 变暗依赖前端 setTimeout 添加的 `.ready`（约 0.9s 后生效） | Functional — 定时器竞态（组件快速销毁重建）若未正确清理，会导致 hover 高亮永久失效 |
| 面积图无鼠标交互高亮 | 新增 mousemove 最近系列检测与高亮/变暗 | Cross-Module/Performance — 新增高频 DOM 事件计算，分面/多系列图表下正确性与性能需验证 |
| 面积填充各自独立半透明 | 相邻系列重塑为不重叠色带 | Rendering — 多系列堆叠面积图视觉呈现改变 |
| 折线/面积 ghost fill 独立淡入 | ghost fill 与主线擦除动画同步 | Rendering — 视觉同步性变化，需人工比对 |

## 第三部分：风险识别（Risk Identification）

- **Functional**：`.ready` 门控依赖前端 `setTimeout` 与后端 `data-last-delay` 属性双端配合；组件快速销毁重建、SVG 重复注入等场景下若定时器未被正确清理（代码已加入 `readyHandle` 清理与 `teardownAreaHover`），仍需验证竞态路径。
- **Rendering**：stagger 从"随元素数量增长"改为"固定 2s 窗口"，元素数量差异极大的图表（2 个系列 vs 50 个系列）动画观感差异被放大，需与设计稿人工比对确认符合预期。
- **Data Consistency/Cross-Module**：面积图鼠标高亮依赖 `.inetsoft-area` 与 `.inetsoft-line` 分组按 DOM 顺序一一对应（假设"面板×系列"顺序严格一致）；分面（facet）图表、多面板堆叠面积图若该顺序假设被打破，会导致鼠标高亮错误匹配系列。
- **默认行为变化/向后兼容性**：柱状图默认动画从"生长"变为"淡入"，是默认行为改变而非新增可选项；已依赖旧视觉效果的用户培训材料、演示视频、回归基线需要同步确认。
- **Performance**：面积图新增鼠标移动时对每个系列做二分查找（每次最多 25 次路径采样），多系列、多分面、高频移动场景下需验证性能表现。
- **边界情况**：单一数据点/单一系列（count=1）时 `staggerDelay` 恒返回 0；各图表在无标注元素（如 `points.isEmpty()`）时的提前 return 分支由 `return;` 改为 `return 0;`，需确认所有调用方对"0 延迟"与"无动画"语义的处理一致，不会误判为"已产生动画"从而错误设置 `data-last-delay`。
- **Cross-Module（导出/打印）**：折线/面积动画时长、擦除方式的裁剪（clip-path）属性变化，需确认导出为 PDF/Excel/Image 及打印预览捕获的最终静态图形不受动画中间态影响。
- **说明（非本次 PR 改动，仅供知悉）**：`Map/Map Contour`（地图坐标系图表）、`3D Bar`、`3D Pie`、`Parabox`（平行坐标图）这四类图表**不支持入场动画**

## 第四部分：测试策略设计（Test Design）

- **核心验证点**：
  1. 各图表类型动画时长（0.8s）、缓动（ease-out）是否统一生效；
  2. 不同元素数量（1 个、2 个、多个如 20+）下 stagger 首尾延迟是否符合"固定 2s 总窗口"规则；
  3. 柱状图默认淡入效果（而非旧"生长"效果）渲染是否正确；
  4. `.ready` 门控：动画播放期间 hover 变暗不应触发，动画结束后（约 0.9s）hover 应正常生效；
  5. 面积图鼠标就近高亮：目标系列保持不透明，其余系列变暗，移出图表区域后恢复。
- **高风险路径**：
  - 快速切换/重新加载 viewsheet（SVG 被替换）时，`.ready` 定时器与面积 hover 事件监听器是否正确清理并重建；
  - 分面图表下面积/折线 hover 高亮是否严格限定在对应面板内，不跨面板误触发；
  - 数据点数量剧烈变化（1 个 → 大量）时 stagger 节奏表现。
- **涉及模块**：Chart Viewer 渲染（SVG 内联指令）、Composer 预览、Export/Print（PDF/Excel/Image 导出静态状态）、Dashboard 多图表联动、Embed iframe 场景（跨生命周期的指令销毁/重建）。
- **专项检查**：
  - 本地化：无用户可见文本变更，无需本地化测试。
  - 配置检查：`BAR_GROW_ENABLED` 等为 Java 编译期常量，非 SreeEnv 属性，无需环境属性/重启验证。
  - 脚本兼容：未新增 Viewsheet 脚本 API，无需 script 兼容性检查。
  - 文档一致性：若用户文档/培训材料展示了柱状图旧"生长"动画效果截图，需确认是否需同步更新。
- **Mobile 影响检查**：面积图新增基于 `mousemove` 的交互，触屏设备无原生对应事件，需验证该功能在触屏端是否有替代方案或仅对桌面端生效、不引发异常。
- **Print Layout/Export 影响检查**：动画时长与 ghost fill/clip-path 裁剪方式改变，需验证静态导出（PDF/Excel/PNG）及打印预览捕获的最终图形（应为动画结束态）在各图表类型下符合设计预期，尤其面积色带重塑与折线擦除裁剪逻辑。

### 图表类型测试覆盖分级（按风险修正）

复核 diff 后发现，本次改动分两层，风险分布并不均匀，**不应对全部图表类型做同等深度的手工验证**：

- **通用层（低风险）**：多数类型只是把原来"各写各的"delay 计算换成调用共享的 `AnimationConstants.staggerDelay(index, count)`，原有排序/分组逻辑未改动。这一层的数值正确性已由 PR 同步更新的 Java 单测（`SVGAnimationDOMInjectorTest.java`）覆盖，QA 不需要逐类型手工量时间验证。
- **独有逻辑层（高风险）**：少数类型除了套用共享公式外，还包含全新的、独有的实现——这些地方才是本次 PR 真正容易出 bug 的地方，需要重点人工验证。

按此分为三档：

**第一档 — 重点覆盖（需完整场景验证）**：Bar、Area、Mekko、Icicle、Sunburst

| 图表类型 | 独有变更点 | 适用场景 |
|---|---|---|
| 柱状图 Bar | 新增默认动画分支（淡入 vs 生长），与共享 stagger 重构无关 | 场景 1（核心）、2/3、5、8、9 |
| 面积图 Area | 全新鼠标就近高亮功能 + 面积色带（band）重塑，与共享 stagger 重构无关 | 场景 2/3、5（含 hover 监听器清理）、6/7（核心）、8（band 重塑重点）、9、10（核心） |
| 马赛克图 Mekko | delay 本是二维(行,列)对角线公式，非单一序号；新增 `rawMax`/`scale` 换算把对角线公式塞进固定窗口——单行/单列时存在除零边界风险 | 场景 2/3（核心）、5、8、9（边界值重点） |
| 层级图 Icicle | 原为"按深度分组"，非单一序号；新增全局 `staggerOrder` 排序 + 索引映射数组（`cellStaggerPos`），易出现索引错位 | 场景 2/3（核心）、5、8、9 |
| 旭日图 Sunburst | 原为"环形分组"，非单一序号；新增全局 `staggerOrder` + 索引映射数组（`arcStaggerPos`），易出现索引错位 | 场景 2/3（核心）、5、8、9 |

**第二档 — 代表性验证（验证共享 `.ready` 门控机制，选 1 个代表即可，无需在 candle/box/radar/treemap 上重复）**：Point

| 图表类型 | 说明 | 适用场景 |
|---|---|---|
| 散点图 Point | 代表 candle/box/radar/treemap 共用的 `.ready` 门控 hover 实现（该机制是共享代码，验证一次即可覆盖所有 A1 类型的门控逻辑本身；具体 delay 数值仍由单测覆盖） | 场景 4（核心）、5 |

**第三档 — 轻量抽查（仅做基础可视化冒烟检查，确认动画能正常播放、无报错、hover 门控生效即可，不需要逐一验证 delay 数值）**：Candle、Box、Radar、Treemap、Line

| 图表类型 | 说明 |
|---|---|
| 蜡烛图 Candle / 箱线图 Box | 仅套用共享的 X 坐标排序 + `staggerDelay`，无独有逻辑 |
| 雷达图 Radar / 矩形树图 Treemap | 仅套用共享公式 + `.ready` 门控（机制已由 Point 代表验证），无独有逻辑 |
| 折线图 Line | 时长从 1.2s 改为 `DURATION`(0.8s) 属简单替换，无独有算法重写；仍建议在场景 8（导出/打印）中覆盖，因涉及 clip-path 裁剪属性变化 |

**跳过 / 仅基础回归**：Pie — 本次 diff 未修改其内部逻辑，仍使用独立的 `PIE_*` 常量，只需确认现有功能未被牵连即可，无需覆盖专项场景。

**执行建议汇总**：
- 场景 1（默认淡入）：仅 Bar。
- 场景 2/3（stagger 窗口）：重点验证 Bar/Area/Mekko/Icicle/Sunburst 五类（各自算法独立重写，风险最高）；Point/Candle/Box/Radar/Treemap 的 delay 数值已由单测覆盖，人工侧仅需冒烟确认动画正常播放。
- 场景 4（ready 门控 hover）：以 Point 为代表验证机制本身即可，无需在其余 A1 类型上重复执行完整流程。
- 场景 5（快速切换回归）：第一档 + Point 代表验证；其余轻量抽查即可。
- 场景 6/7（面积图 hover 高亮）：仅 Area。
- 场景 8（导出/打印）：建议覆盖全部有渲染/裁剪相关变更的类型（Bar、Line、Area、Mekko/Icicle/Sunburst），Candle/Box/Radar/Treemap 可降级为抽查。
- 场景 9（单元素边界）：重点覆盖第一档五类（尤其 Mekko 的除零边界），其余抽查。
- 场景 10（移动端）：核心是 Area（新增鼠标交互的触屏降级），其余类型仅需确认基础显示正常。
- Pie：不纳入专项场景，走常规回归即可。

## 第五部分：核心测试场景（Key Test Scenarios）

### 场景 1：柱状图默认入场效果验证
- **Scenario Objective**：验证柱状图新建/刷新后默认呈现淡入效果，而非旧版"从底部生长"效果。
- **Scenario Description**：本次改动调整了柱状图动画默认表现，若未正确生效，用户会看到与设计规范不符的动画效果，影响多图表间的视觉一致性体验。
- **适用图表类型**：柱状图（Bar），唯一存在该默认行为变化的类型。
- **Key Steps**：
  1. 打开一个包含柱状图的Viewsheet；
  2. 刷新/重新加载该图表，观察柱子出现的动画方式。
- **Expected Result**：柱子以透明度渐显的方式出现，不出现从基线向上/向左"拉伸生长"的缩放动画。
- **Risk Covered**：默认行为变化、向后兼容性。

🔴 **测试-分析**： 符合预期

### 场景 2：小数据量图表的动画间隔节奏
- **Scenario Objective**：验证图表数据点很少（如 2 个系列/2 个数据点）时，动画整体错落节奏符合新设计规范。
- **Scenario Description**：本次改动将错落间隔从"随数据量增长"改为"固定总时长"，数据量很少的图表动画耗时可能因此明显变长，需确认该体验符合预期而非"卡顿感"。
- **适用图表类型**：重点覆盖第一档 **Bar、Area、Mekko、Icicle、Sunburst**（各自 stagger 算法独立重写，需逐一验证）；**Point** 作为 A1 代表验证一次；Candle/Box/Radar/Treemap/Line 仅做冒烟抽查（不需要精确量时间）。
- **Pre-condition**：分别准备上述每种图表类型仅含 2 个系列/元素的版本（如折线图两条线、马赛克图 1 行 2 列、旭日图两个同级扇区）。
- **Key Steps**：
  1. 逐一打开每种图表并触发入场动画；
  2. 观察每种图表中第一个元素与第二个元素开始动画之间的时间间隔。
- **Expected Result**：各图表类型中两个元素的动画开始时间间隔均应达到设计规定的固定错落窗口（约 2 秒），且整体动画观感自然，不显得突兀或过慢。
- **Risk Covered**：默认行为变化、边界条件。

🔴 **测试-分析**： 符合预期

### 场景 3：大数据量图表的动画间隔节奏
- **Scenario Objective**：验证图表数据点很多时，动画总时长不随数量线性增长。
- **Scenario Description**：验证"总错落窗口固定"的设计意图在大数据量场景下真正生效，避免出现历史版本中"数据越多动画越久"的问题。
- **适用图表类型**：重点覆盖第一档 **Bar、Area、Mekko、Icicle、Sunburst**（数据量大时最容易暴露排序/索引映射错误）；**Point** 代表 A1 类型验证一次；Candle/Box/Radar/Treemap/Line 冒烟抽查即可。
- **Key Steps**：
  1. 分别打开每种图表类型的大数据量版本（如 30+ 数据点的散点图、多行多列的马赛克图、多层级的旭日图/层级图）；
  2. 触发入场动画，记录每种图表首个元素与最后一个元素出现的时间差。

### 场景 9：单系列/单数据点图表的动画边界情况
- **Scenario Objective**：验证仅有单个系列或单个数据点的图表，动画和交互功能均正常，不出现异常或报错。
- **Scenario Description**：错落间隔算法在元素数量为 1 时需要特殊处理（不产生分母为 0 的计算）；**马赛克图（Mekko）尤其需要重点验证**——其对角线 stagger 改为按 `rawMax = maxColIdx*COL_RATIO + maxRowIdx*ROW_RATIO` 计算缩放系数，当图表只有单行或单列（`maxColIdx=0` 且/或 `maxRowIdx=0` 导致 `rawMax=0`）时存在潜在除零风险，是本次改动中最需要单独验证的边界场景。
- **适用图表类型**：**Mekko（核心，单行/单列边界）**；同时覆盖 Bar、Area、Icicle、Sunburst、Point 的单元素/单系列情况作为常规边界检查。
- **Pre-condition**：分别创建：① 仅 1 行或 1 列的马赛克图（核心用例）；② 仅单一系列/单一数据点的柱状图、面积图、层级图、旭日图、散点图。
- **Key Steps**：
  1. 依次打开上述每个边界图表，观察入场动画是否正常播放（重点关注马赛克图是否报错或延迟计算异常，如 NaN/Infinity）；
  2. 鼠标悬停在唯一的系列/数据点上，观察高亮表现。
- **Expected Result**：所有边界图表动画均正常播放（无延迟异常、无 NaN/报错），悬停高亮功能正常工作；马赛克图在单行或单列时动画延迟应回退为合理默认值（如 0 或 scale=1.0 的兜底逻辑），不出现除零导致的渲染异常。
- **Risk Covered**：边界条件、计算异常。
